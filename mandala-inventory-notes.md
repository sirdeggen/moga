## Concrete Go engine storage

- [`overlay-go/internal/enginestore/enginestore.go`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/internal/enginestore/enginestore.go) declares `type Store` and compile-time asserts `var _ engine.Storage = (*Store)(nil)`. It is a Mongo-backed implementation of `go-overlay-services` v1.3.2 `engine.Storage`.
- `Store` uses three Mongo collections: `engineOutputs` (inline BEEF bytes, topic/txid/vout unique index and merkle/spend fields), `engineAppliedTransactions` (topic+txid unique), and `engineInteractions` (host+topic unique). It implements the full pinned interface, plus compensation/eviction/activity helpers (`UnmarkSpentBySpendTxid`, `FindOutputsByTxid`, `DeleteOutputsByTxid`, `RawTxHexByTxid`).
- This is concrete, engine-wired, Docker-packaged source with tests in `enginestore_test.go`; production suitability and any live deployment remain unverified. The default wiring uses a permissive `scriptsOnlyTracker` when `ARCADE_URL` is unset, and the package comments say GASP sync is off, so the source should not be treated as a demonstrated production node.

## Bounded capability gaps in Mandala source

- **Atomicity:** `enginestore.InsertOutputs` performs one Mongo `BulkWrite`, while spend updates, applied-transaction inserts, and Mandala projection changes are separate operations. `wiring.App` explicitly documents that pinned engine v1.3.2 marks inputs/projections before broadcast and requires a compensation closure on broadcast failure. The HTTP submit path says mid-commit storage faults have no clean inverse. This is evidence of compensating behavior, not a cross-collection transaction/outbox guarantee.
- **Durable ACK/index/outbox:** `engineAppliedTransactions` is a duplicate gate and `engineInteractions` stores GASP last-interaction scores; no durable publish/ACK outbox or retry worker appears in the inspected Go source. The default Go wiring has no GASP sync configuration and no advertiser. The source includes Arcade callbacks only when `ARCADE_URL` is configured.
- **Inline BEEF size:** BEEF bytes are stored inline in each `engineOutputs` Mongo document and copied into every admitted output document. No chunking/GridFS or explicit size guard appears in the store. Mongo’s BSON document limit therefore remains an operational constraint; exact maximum behavior was not load-tested here.
- **Cursor/BASM depth:** `/admin/activity` has an inclusive timestamp cursor and dedupe guidance, while engine UTXO paging uses `score > since` sorted by score. This is source-level pagination, not evidence of a complete BASM-compatible cursor contract across all APIs. `/lookup` explicitly leaves binary aggregation mode out of scope.

Mandala pins `go-overlay-services v1.3.2`, so this is a separate compatibility line.
- The current [`storage/event_data.go`](https://github.com/b-open-io/overlay/blob/65dec0e7cfc0c29968fe43b082bbde9a6bd94f6c/storage/event_data.go) does now contain methods named `FindOutpointsByMerkleState`, `ReconcileMerkleRoot`, and `LoadAncillaryBeef`, and README advertises PostgreSQL/Mongo/SQLite backends. However its `TopicDataStorage` signatures still use topic-scoped methods and `beef []byte` (for example `InsertOutputs(ctx, txid, ..., beef []byte)`), unlike Mandala’s v1.3.2 interface (`topic` argument and `*transaction.Beef`). Therefore it is a potential maintained storage owner/alternative library, but not a drop-in adapter for Mandala’s pinned engine based on immutable source signatures.
- b-open-io has route helpers and a `cmd/bootstrap` libp2p bootstrap executable, but the repository tree has no application server `main` that assembles a complete Mandala-style host. [`routes/submit.go`](https://github.com/b-open-io/overlay/blob/65dec0e7cfc0c29968fe43b082bbde9a6bd94f6c/routes/submit.go) owns a Fiber submit route and optional libp2p/HTTP peer broadcasting. Its asynchronous broadcasts use `context.Background()` and log failures, so they are not a durable ACK/outbox guarantee.
