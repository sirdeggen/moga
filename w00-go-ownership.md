## Go client and generic host findings

The current SDK [`LookupResolver.Query`](https://github.com/bsv-blockchain/go-sdk/blob/50502c819a9ca8d6cfab4c100288073362895d9b/overlay/lookup/resolver.go#L74) collects a host list, runs host goroutines, waits on the wait group, then aggregates responses. It parses BEEF to derive outpoint keys but has no progressive return contract on this method. [`FindCompetentHosts`](https://github.com/bsv-blockchain/go-sdk/blob/50502c819a9ca8d6cfab4c100288073362895d9b/overlay/lookup/resolver.go#L152) is the SLAP discovery owner. Context/timeouts are existing seams, not evidence that all proposed scheduling/backpressure/verification guarantees exist.

Go [`identity.Client`](https://github.com/bsv-blockchain/go-sdk/blob/50502c819a9ca8d6cfab4c100288073362895d9b/identity/client.go#L240) delegates to the [`wallet.Interface` discovery methods](https://github.com/bsv-blockchain/go-sdk/blob/50502c819a9ca8d6cfab4c100288073362895d9b/wallet/interfaces.go#L62); the concrete toolbox discovery implementation is [`pkg/wallet/wallet.go`](https://github.com/bsv-blockchain/go-wallet-toolbox/blob/c36c5db248124ea42494223e067d20eed63835a0/pkg/wallet/wallet.go#L1228). These are client ownership seams, not the identity server. The [identity-server follow-up](go-identity-server-ownership.md) records the missing Go topic/lookup implementation and a minimal companion-package proposal. Wallet action/storage rewrites are not needed to close that server gap.

The current generic [`engine.Storage`](https://github.com/bsv-blockchain/go-overlay-services/blob/f5d8074be085c1970e113bc8ee55fecbab251fcf/pkg/core/engine/storage.go#L15) is injected into `engine.Config`. [`OverlayGASPStorage`](https://github.com/bsv-blockchain/go-overlay-services/blob/f5d8074be085c1970e113bc8ee55fecbab251fcf/pkg/core/engine/gasp-storage.go) adapts GASP to that engine; it is not a concrete engine persistence implementation. Current source tree/code searches still locate no production engine-storage adapter or BASM implementation inside this standalone repository. This remains a bounded source result.

The [`pkg/server` HTTP host](https://github.com/bsv-blockchain/go-overlay-services/blob/f5d8074be085c1970e113bc8ee55fecbab251fcf/pkg/server/server_http.go#L177) defaults to `NewNoopEngineProvider()` unless an engine is supplied with `WithEngine`. Its `/metrics` Fiber monitor is not a per-topic synchronization console. The [no-op provider's own description](https://github.com/bsv-blockchain/go-overlay-services/blob/f5d8074be085c1970e113bc8ee55fecbab251fcf/pkg/server/internal/adapters/noop_engine.go#L16) identifies it as a mock/temporary implementation. Thus running the documented example alone does not identify a production database-backed overlay deployment. S07 must deliver coherent real engine/storage startup; no deployed Go host owner has been established from these sources.

## New concrete adapter evidence: Mandala

Mandala's [`Store`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/internal/enginestore/enginestore.go) has a compile-time `engine.Storage` assertion and uses Mongo collections `engineOutputs`, `engineAppliedTransactions` and `engineInteractions`. Its [`wiring.Build`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/internal/wiring/engine.go) passes that store to the engine alongside `tm_mandala`/`ls_mandala`. [`go.mod`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/go.mod) uses module `github.com/sirdeggen/mandala/overlay-go`, Go 1.25.4, go-overlay-services v1.3.2, go-sdk v1.2.24 and Mongo driver v2.7.0. Its internal package cannot simply be imported as a generic external adapter.

| Approved reliability requirement | Bounded Mandala evidence / gap |
| --- | --- |
| Atomic admission/indexing and durable acknowledgment | Store methods use individual Mongo operations/BulkWrite; engine/domain projections are separate. Wiring supplies broadcast-failure compensation. The [`submit handler`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/internal/httpapi/submit.go) describes storage-failure compensation limitations. No cross-collection admission transaction or durable acknowledgment/index-publication contract was demonstrated. |
| Durable propagation/index outbox | No durable outbox/retry worker was evidenced in the inspected store/wiring/submit path. A successful source-level submit is not proof of reliable peer delivery. |

| BASM | Source search found BASM in planning/specification documents, not an implementation in the inspected Go host/store. Historical recovery/status remains future work. |
| Mandatory independent chain verification | With no `ARCADE_URL`, wiring uses a permissive `scriptsOnlyTracker`. Configurable chain/broadcast wiring exists, but this default is not an independently verified production reference for the approved plan. |
| Startup/operator UI | [`cmd/overlay`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/cmd/overlay/main.go) and [Dockerfile](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay-go/Dockerfile) provide concrete host packaging; [`Compose`](https://github.com/bsv-blockchain/mandala/blob/488bedb8dfaa5cb912bc72d2decc576923adc2ae/overlay/docker-compose.yml) leaves Go commented out and TS enabled.
