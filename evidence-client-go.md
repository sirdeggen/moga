## Confirmed TypeScript behavior

### LookupResolver discovery and progressive lookup

- A lookup query resolves competent hosts once, then ranks that array before starting host queries. `query$()` captures that ranked list and its `hostCount` for the session; host discovery is not re-run while that session progresses ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:920), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1115)). This is the current fixed per-query host snapshot.
- SLAP discovery itself returns as soon as one tracker yields a valid host (subject to availability mode), while remaining trackers continue in the background; discovered hosts are deduplicated in a `Set` and first-seen tracker attribution is retained ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1272), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1291)). Thus “fixed snapshot” describes the consumer query after discovery, not a globally synchronized tracker result.
- `query$()` emits cumulative output snapshots. Default progressive mode can emit after the grace window (80 ms by default), then on late new outputs, and finally after every in-flight host settles; `waitForAllHosts` changes the first-emission behavior ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:590), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:697), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1102)). `queryDetailed()` explicitly opts into waiting for all bounded host settlements before taking its first emission ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:835)).
- Aggregation deduplicates by resolved `txid.outputIndex`; the resolver accepts any nonempty supplied `txid` string without binding it to the transaction bytes in this helper, and otherwise parses BEEF, memoized by the serialized BEEF bytes with a bounded/TTL cache ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:590), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1336)). Octet-stream responses also deduplicate BEEF extraction work per txid while preserving each requested output index ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:447)).
- The octet-stream extraction loop yields to the event loop between outputs, and the resolver’s comments document bounded per-host timeout cleanup on early iterator break ([LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:466), [LookupResolver.ts](/Users/personal/git/ts-stack/packages/sdk/src/overlay-tools/LookupResolver.ts:1113)). This supports a buffered/progressive transport reading, but does not by itself prove transport-level backpressure beyond the session queue.

### Certificate verification and identity discovery

- `identityUtils.parseOne()` constructs a certificate, decrypts fields, calls `await verifiableCert.verify()`, and then stores decrypted fields. Any thrown parse/decrypt/verify error is caught and converted to `null`, so malformed or invalid entries are skipped ([identityUtils.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/utility/identityUtils.ts:135)). The `verify()` result is not assigned or checked there ([identityUtils.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/utility/identityUtils.ts:156)). Separately, this path does not verify that the containing transaction or its Merkle proof is valid; it parses `Transaction.fromBEEF` and the output script, then verifies only the certificate signature. That transaction/proof omission is distinct from the ignored boolean.
- `Certificate.verify()` is typed `Promise<boolean>` and returns the `valid` result ([Certificate.ts](/Users/personal/git/ts-stack/packages/sdk/src/auth/certificates/Certificate.ts:208)). In the current internally constructed `ProtoWallet` path, `verifySignature()` throws `ERR_INVALID_SIGNATURE` when the cryptographic result is false and only returns `{ valid: true }` on success ([ProtoWallet.ts](/Users/personal/git/ts-stack/packages/sdk/src/wallet/ProtoWallet.ts:297)). Therefore an invalid certificate signature reaches `parseOne()` as a throw and is dropped. The explicit success check is still the proposed contract for a robust caller, but no current invalid-signature vulnerability was established from this path.
- Wallet discovery validates identity-key shape, attributes, `limit` default 10/max 10,000, non-negative `offset`, and defaults `seekPermission` to false ([validationHelpers.ts](/Users/personal/git/ts-stack/packages/sdk/src/wallet/validationHelpers.ts:1170), [validationHelpers.ts](/Users/personal/git/ts-stack/packages/sdk/src/wallet/validationHelpers.ts:1217)). This differs from the interface-level prose that describes a default-true permission setting; the validator is the current behavior, pending a focused compatibility decision. The wallet-toolbox discovery implementation uses a two-minute trust-settings cache and two-minute overlay-result cache; it sorts trusted certifier keys into the cache key and filters returned certificates by configured certifier trust/threshold ([Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:788), [Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:820), [identityUtils.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/utility/identityUtils.ts:38)). The toolbox’s overlay helper currently does not forward the validated discovery `limit`/`offset`; it queries by identity/attributes and certifiers, then applies trust transformation ([Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:832), [Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:890)). This is a confirmed boundary worth preserving/clarifying; whether it is an intentional API contract or a defect is unresolved here.
- Identity-resolution permission is configuration-gated in `WalletPermissionsManager`; when enabled, both discovery methods seek protocol `[1, 'identity resolution']` with the supplied originator before forwarding ([WalletPermissionsManager.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts:435), [WalletPermissionsManager.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/WalletPermissionsManager.ts:5013)). Local contacts can short-circuit overlay discovery and synthetic contact trust defaults to `Infinity`, which is a separate trust boundary from certificate-based overlay results ([Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:157), [Wallet.ts](/Users/personal/git/ts-stack/packages/wallet/wallet-toolbox/src/Wallet.ts:808)).
- Existing Verifast APIs are BDK verifier/batch/worker entry points (`BdkVerifier`, `BdkBatch`, worker pool/protocol) and the package exports browser/node verifier modules; no source edit or API change was made. The relevant package paths are [BdkVerifier.ts](/Users/personal/git/ts-stack/packages/verifast/src/BdkVerifier.ts:1), [BdkBatch.ts](/Users/personal/git/ts-stack/packages/verifast/src/BdkBatch.ts:1), and [BdkWorkerPool.ts](/Users/personal/git/ts-stack/packages/verifast/src/workers/BdkWorkerPool.ts:1). Chain/cache evidence in scope includes the wallet’s two-minute discovery caches above; a broader chain-tracker cache audit was outside this bounded pass.

## Brief Go inventory and risks

- The Go engine exposes a broad `engine.Storage` interface covering output insertion/find/delete, spent-state and consumed-by updates, BEEF updates, applied-transaction records, interaction scores, Merkle state, and ancillary BEEF loading ([storage.go](/Users/personal/git/go/go-overlay-services/pkg/core/engine/storage.go:15)). `OverlayGASPStorage` is a GASP storage adapter, not a concrete implementation of `engine.Storage`; it delegates GASP reads and input discovery to the engine’s injected `Engine.Storage` ([gasp-storage.go](/Users/personal/git/go/go-overlay-services/pkg/core/engine/gasp-storage.go:62)). The remaining implementations found in scope are test fakes; no production Mongo/Postgres implementation of the engine `Storage` interface was found in these checked repositories.
- `BASM` has no occurrences in the checked Go repositories (`go-overlay-services`, `go-overlay-discovery-services`, `go-bsv-middleware`); this is absence evidence limited to those paths/commits, not a claim about other repositories or dependencies.
- The engine commit sequence deletes spent UTXOs, inserts admitted outputs, notifies lookup services (SHIP/SLAP included), updates consumed-by references, then records the applied transaction ([engine.go](/Users/personal/git/go/go-overlay-services/pkg/core/engine/engine.go:592)). Each step returns on error, but the sequence is not shown inside one storage transaction or compensating rollback. A failure after an earlier successful step can therefore leave partial state; this is a source-level risk, not a reproduced failure.
- Network propagation is performed separately and errors are logged after broadcaster creation/broadcast failure; the propagation error does not return from the commit path ([engine.go](/Users/personal/git/go/go-overlay-services/pkg/core/engine/engine.go:689)). This establishes best-effort propagation semantics in the inspected path.
- Go SHIP and SLAP storage each create only a non-unique compound query index (`domain,topic` and `domain,service`) and insert records directly. Deletion identifies `(txid,outputIndex)`, but neither `EnsureIndexes` declares that pair unique ([SHIP storage.go](/Users/personal/git/go/go-overlay-discovery-services/pkg/ship/storage.go:47), [SLAP storage.go](/Users/personal/git/go/go-overlay-discovery-services/pkg/slap/storage.go:44)). The source therefore supports the review concern that a unique outpoint index/idempotent write policy is still a design need; duplicate prevention was not proven by the checked implementation.
- Pagination validation accepts non-negative `limit`/`skip` and asc/desc, while Mongo options apply sort/skip/limit; this bounds query shape but does not establish a stable tie-breaker ordering for records sharing the same indexed fields ([shared lookup.go](/Users/personal/git/go/go-overlay-discovery-services/pkg/shared/lookup.go:18), [shared storage.go](/Users/personal/git/go/go-overlay-discovery-services/pkg/shared/storage.go:24)).
