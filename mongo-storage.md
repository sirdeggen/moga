# MongoDB storage and migration design for Overlay-owned state

**Status:** proposal only. This specifies an additive MongoDB adapter and operations path. It neither changes the SQL default nor migrates, deploys, or modifies any source database.

## Scope and evidence

The boundary is durable state owned by an Overlay node: admitted outputs/history, transaction/BEEF/proof material, topic application records, GASP cursors and temporary graphs, BASM anchors, SHIP/SLAP discovery, bans, and propagation recovery. This proposes equivalent logical storage contracts for TS and Go; a shared physical format and concurrent-writer topology require separate version/conformance approval. It is not a wallet schema.

Excluded: advertiser wallet storage, any wallet-toolbox provider rewrite, sessions and payments, and external chain, proof, or broadcast services. Those stay outside the overlay persistence boundary.

Its present interface cannot wrap a submission in one transaction or enlist arbitrary lookup services.

- Go defines corresponding engine storage ([storage.go](/Users/personal/git/go/go-overlay-services/pkg/core/engine/storage.go:15)) and GASP graph ([storage.go](/Users/personal/git/go/go-overlay-services/pkg/core/gasp/storage.go:9)) interfaces. This review found no production Mongo engine adapter in that repository: one is proposed, not claimed to exist.

All proposed hashes are normalized lower-case 64-character hex. Serialize scripts, raw tx, BEEF, and Merkle paths as BSON BinData, never JSON byte arrays.

## Deployment and consistency

Use a dedicated Atlas database per overlay deployment/network, on a multi-node replica set. Every common-schema key includes `network` and `genesisHash`; node-owned state also includes `nodeId`/deployment scope, so distinct networks and nodes never share an authority namespace accidentally. Durable transitions use `{w:"majority", j:true}`; reads that gate admission use primary/majority reads. Standalones do not support transactions; replica sets do ([MongoDB transactions](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/#availability)).

Start unsharded. The model depends on global txid/outpoint uniqueness and short single-database transactions. If sharding later becomes necessary, every cross-shard unique index must start with the full shard key ([MongoDB limits](https://www.mongodb.com/docs/manual/reference/limits/#unique-indexes-in-sharded-collections)). Retry a `TransientTransactionError` by rerunning the complete logical body under its operation id; for `UnknownTransactionCommitResult`, retry/reconcile the same commit identity before a new body is allowed. Keep transactions below the default one-minute lifetime and avoid cache pressure ([production considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/#runtime-limit)): no BEEF parsing, verification, network I/O, plug-in call, or GridFS upload in a transaction.

## Collections and indexes

All documents have `schemaVersion`, `createdAt`, and `updatedAt` where useful. Names and fields below are proposals. Every abbreviated identifier and index below is prefixed by `scope=(network,genesisHash,nodeId)` unless explicitly identified as immutable, scope-independent content; the physical field prefix is mandatory when one database holds more than one scope.

Avoid dynamic user keys, dotted names, and large indexed arrays. BSON documents max at 16 MiB and a collection supports at most 64 indexes ([limits](https://www.mongodb.com/docs/manual/reference/limits/#bson-documents), [indexes](https://www.mongodb.com/docs/manual/reference/limits/#indexes)).

## Admission, acknowledgment, and recovery

Add an optional `commitAdmission(operation)` capability in TS and Go. Existing individual methods continue for SQL compatibility; Mongo uses the capability only when explicitly selected and the engine has been changed to call it. A legacy call sequence cannot be advertised as a whole-submission atomic/durable-ack path. TS retains its current/default selection and only gains an explicit Mongo option. Go currently has injection-oriented storage interfaces and no located production Mongo adapter, so it retains injection and gains an explicit factory/profile; it must not invent a global SQL default. No default changes.

Existing parse/SPV/topic decision/broadcast behavior stays outside it. In one short Mongo transaction, Mongo:

1. claims `overlay_submission_ops` by idempotency key and verifies its request digest; a matching completed retry returns the saved STEAK, a mismatched reuse fails;
2. upserts already-published payload references and transaction metadata; inserts topic outputs/edges; conditionally marks spends, rejecting a different spender;
3. upserts applied/proof/anchor work state; and
4. inserts lookup and propagation outbox records plus the completed STEAK.

Version/check the state read by topic admission and revalidate its read-set predicates during commit; if state changed, recompute the decision outside the transaction and retry under the same logical identity. An admission digest binds semantic raw transaction/topic/mode/policy inputs; independently validated later proof variants update proof state without falsely becoming an idempotency conflict or permanently excluding better evidence. Define exact integer encodings for satoshis/heights/indices in the shared conformance schema; TS must not round BSON integer values through unsafe JavaScript numbers.

Return the acknowledgment only after majority commit. A crash retry returns the exact saved acknowledgment. The driver must distinguish retry labels: `TransientTransactionError` reruns the complete logical transaction body under the same operation id after rereading its state; `UnknownTransactionCommitResult` retries/reconciles the same commit identity before any fresh body execution. Unique admission/outpoint keys and conditional spend writes give deterministic concurrent behavior. With existing broadcast-before-mutation ordering, a broadcast may repeat; local state remains exactly once.

Native Mongo lookup/index implementations that use the same session can enlist their writes in the admission transaction. External callbacks and plug-ins cannot. For the latter, persist an event in the transaction; a leased worker delivers with the event idempotency key and retries until acknowledged. The plug-in/replay capability is additive: do not assume an existing plug-in is replay-safe. Until it declares idempotency plus a rebuild/reconciliation contract, its external index is asynchronous and may lag; it cannot participate in read-your-write guarantees. The propagation outbox uses the same protocol, so STEAK means only durable overlay admission, never remote delivery or external-index visibility. A readiness report may expose required durable-store health and outbox lag, but must not mark an external index caught up unless its own checkpoint confirms it.

SHIP/SLAP writes can join the transaction only when local and on this database/session. Remote advertiser/wallet operations cannot. For bans, transactionally write the ban and delete/suppress local discovery records, then enqueue other lookup evictions. A ban is serving/index moderation, distinct from canonical historical admission/BASM evidence: do **not** put a local ban in the canonical historical-admission predicate or delete that history. Existing code that filters new SHIP/SLAP admittance is a compatibility behavior requiring an explicit product decision before it can be changed.

## Large raw transactions and BEEF

MongoDB recommends GridFS for files above 16 MiB, but GridFS does not support multi-document transactions ([GridFS](https://www.mongodb.com/docs/manual/core/gridfs/#when-to-use-gridfs)). Therefore payload upload is outside admission commit.

1. Stream canonical bytes, calculate SHA-256/length, and reserve/observe `overlay_payloads[digest]` in `uploading`; reuse a ready digest.
2. Upload a new GridFS `overlayPayloads` file as `staged`, with digest/length/kind/owner/fencing-token metadata. Verify streamed byte count and digest, then mark the GridFS file `published` first.
3. Compare-and-set the small payload metadata from that unexpired owner/token to `ready`, storing its published `fileId`. Admission may reference only `ready` payloads whose GridFS file is published. This order prevents a committed admission from observing a not-yet-public file. Inline BinData uses a conservative ceiling far below 16 MiB including document overhead.
4. GC is a serialized state transition, not a check then delete: in a transaction/CAS shared with every pin/reference creator, the sweeper atomically changes an expired, unpinned `ready → deleting` candidate using its fencing token. New references require `ready` and are prohibited once `deleting` is visible. It then physically deletes GridFS bytes and finalizes `deleted`; crash recovery reconciles/retries a `deleting` record. Before the claim, it reconciles references from transactions, GASP nodes, BASM jobs, and outboxes. This removes the reference-creation versus physical-delete TOCTOU race.

Store raw tx and each proof variant as content-addressed per-transaction objects. A BEEF manifest references those component objects in canonical dependency order; do not rely on whole-BEEF addressing to deduplicate overlapping ancestry. A compact BEEF is reconstructed from the manifest and references. This handles an oversized individual raw transaction and oversized ancestry. Pin payloads required by active admissions, graphs, outbox events, and BASM repair.

## BASM, GASP, and historical state

Historical admissions use the same idempotency primitive with explicit mode and no broadcast/propagation record, matching TS historical behavior ([Engine.ts](/Users/personal/git/ts-stack/packages/overlays/overlay/src/Engine.ts:1040)).

Persist direct proof data with historical admission. Build topic anchors in strict canonical `blockIndex` order: duplicate indices are invalid and must be rejected, never legitimized by a txid tie sort. Then atomically write anchor and canonical tip guarded by `chainEpoch`, `topicHistoryGeneration`, and the pinned canonical header. A same-block historical admission changes the topic’s admitted subset without a reorg: advance topicHistoryGeneration, rebuild that height and all downstream TACs, invalidate comparisons/jobs from the old revision, and do not call it a chain-epoch change. On reorg atomically fence the old chainEpoch, create/advance a new one, mark old anchors noncanonical, demote applied records rather than delete them, and enqueue re-proof/rebuild. BASM recovery cursor/job/comparison writes must filter both generation fields and lease token; a stale worker cannot publish a mixed-generation anchor or green comparison. Keep payloads until reconciliation completes. This follows the TS demotion contract ([Storage.ts](/Users/personal/git/ts-stack/packages/overlays/overlay/src/storage/Storage.ts:227)).

The worker causing a history revision atomically records the old→new generation transition and its own new checkpoint/lease fence; it resumes in that new revision. Other workers observing the old revision restart. This prevents a repair from repeatedly invalidating its own already-committed progress. Rebuilds are staged and bounded; incomplete downstream anchors cannot be published as a contiguous current tip.

GASP pagination orders by `(score,_id)` only for a negotiated wire version that carries the tuple. Advance a peer cursor only after finalization. Do not assume legacy numeric-`since` is inclusive: use overlapping numeric continuation only when the peer capability/protocol definition proves an inclusive, fully drained equal-score page. In that case dedupe by outpoint and advance only after all equal-score candidates finalize. A strict-`since` peer, a finite cap that cannot prove equal-score drain, or an unknown legacy semantic must use a proven no-skip bounded full-resync mode if that peer supports one, or report capability-limited with no cursor advancement. Equal-score/no-skip and strict-`since` conformance tests are mandatory. Node insertion is idempotent by graph/outpoint. A short finalization transaction validates graph state, invokes admission, records cursor handoff, and marks finalized. Recover leased/receiving graphs; discard only invalid/expired work with reason. The Go interface explicitly separates append, validate, discard, and finalize ([GASP storage](/Users/personal/git/go/go-overlay-services/pkg/core/gasp/storage.go:9)).

## Migration, cutover, rollback

This remains additive and opt-in. TS may expose `storageAdapter=sql|mongo` while retaining its current SQL/default selection. Go retains storage injection and may add an explicit Mongo factory/profile only once its adapter exists; it has no assumed global SQL default. Do not dual-write request traffic; there is no atomic cross-store acknowledgment. TS and Go may share records only after a separately versioned schema, binary-format, migration, and cross-language conformance decision; mixed-version concurrent writers are unsupported.

1. **Prepare:** Atlas replica set, TLS/least privilege, PITR/backups, migration ledger/lease, validators/indexes/GridFS, readiness checks.
2. **Backfill:** take a consistent SQL snapshot or maintenance window; publish payloads first; import deterministic IDs; retain proofs, admissions, anchors, and cursors. Stop on any unrepresentable legacy record instead of dropping it.
3. **Verify:** compare topic output and key checksums, spent/proven/unproven counts, raw/proof digests, cursors, anchors/TAC, and sampled BEEF hydration; run read-only shadow lookup/GASP/BASM checks.
4. **Cut over:** quiesce submissions/workers, replay SQL delta to a high-water mark, verify again, explicitly switch adapter, then restart workers. Keep SQL read-only through rollback window.
5. **Rollback:** quiesce Mongo writers and establish one fenced final cutoff. Resume SQL only when there were **no** Mongo-only acknowledged writes after cutover, or after replaying **all** acknowledged Mongo operations through that cutoff into SQL: admissions/spends/evictions, payload manifests and component blobs, proofs, anchors/generation/reorg state, GASP cursors, and required index/outbox checkpoints. Verify the same invariants before reopening SQL writes. If either condition cannot be proved, keep the service read-only and forward-fix; never silently discard post-cutover Mongo state. Do not delete Mongo: retain proofs/admissions/anchors.

## Startup, readiness, and acceptance

Startup connects TLS, pings primary, verifies replica-set transactions/majority journaling, acquires migration lease, validates schema/indexes/GridFS, runs a small transactional probe, checks required payloads ready, and recovers leases/uploads before HTTP/workers. TS already offers distinct live/ready endpoints ([OverlayExpress.ts](/Users/personal/git/ts-stack/packages/overlays/overlay-express/src/OverlayExpress.ts:1883)); readiness fails for unavailable Mongo, incompatible schema, or unresolved required migration.

Monitor primary changes, majority-write latency/errors, transaction retries/aborts, index/payload staging age, outbox depth/age, graph recovery, unproven/anchor lag, reorg repairs, GASP cursor lag, bans, and evictions.

Before production: contract tests in TS/Go against a three-member replica set; duplicate/competing-spender races and kill/retry at every step; both transaction retry labels; Atlas primary failover; GridFS publication plus ready-to-deleting GC/reference-creation races; oversized tx and per-transaction/proof/BEEF-manifest dedupe/corruption cases; GASP negotiated-tuple, proven-inclusive equal-score, strict-since, and finite-cap fallback cases; BASM same-block history revision, reorg/chainEpoch fencing/demotion/reproof; SHIP/SLAP moderation versus historical-admission cases; outbox duplicate/reconciliation and read-your-write-boundary cases; SQL backfill/cutover/rollback replay through a fenced cutoff; and Atlas regional failover plus restore rehearsal.

## Decisions before implementation

Select TS/Go driver versions and retry helpers; Atlas tier/topology/RPO/RTO/retention; maximum accepted tx/BEEF and graph bounds; plug-in idempotency/rebuild contract; and the shared TS/Go BSON/binary/score format. That shared format is a future cross-language proposal; do not permit mixed-version concurrent writers until conformance establishes it. The Go Mongo engine adapter and migration runner are intentionally future work.
